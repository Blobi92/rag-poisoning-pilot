Abstract

Research agents can now produce a complete study in under an hour: question, code, data, report and repository. Does such a result survive verification? We red-team our own team’s RAG-poisoning pilot, which an autonomous agent (Perplexity “Computer”) generated end to end during this sprint. The pilot claims that a source allowlist stops external poisoning (18/20 → 0/20) and that content verification against the canonical source is the only defense that stops a compromised trusted source (18/20 → 0/20). We apply a four-layer audit: code and data, the agent’s session transcript, citations, and a pre-registered reproduction. The headline content-verification result is produced by the code itself: poison is rejected because its document ID contains the string “poison”. The transcript shows that the two “successful” arms were added after the planned arms failed, and that the results file mixes several code versions. Three of six references contain errors, one of which points to an unrelated radiotherapy paper. With the original binary and model hash, the unmodified pipeline reproduces 5 of 7 arms exactly. A pre-registered extension (3 poison sets, 60 trials per arm) makes the threat-model gap concrete. Honest content verification blocks poison only while the canonical source is clean, at the cost of 5.5% of trusted chunks. Once that source is poisoned, it gives no protection (26/60 vs 25/60). Both outcomes follow from the design; what we measure is their cost and a dilution effect. We release a one-command reproduction and a reviewer checklist.

1. Introduction

Agents lower the cost of producing research-shaped artifacts much faster than they lower the cost of checking them. An agent that outputs hypotheses, a seven-arm design, a chart, a limitations section, citations and a GitHub repository has produced every surface signal of rigor. Whether its claims are true is a separate question. We treat that gap as an epistemic-infrastructure problem: what does it take to verify an AI-generated result, and which failure modes should a reviewer expect?

We study our own case. On the final day of this sprint, a team member prompted an autonomous agent with a research question on RAG poisoning. In one 34-minute session, the agent designed, ran, wrote up and pushed the study to GitHub. We then red-teamed it as if a stranger had written it. The topic suits a credibility audit, because it is itself about provenance and verification. The study’s own conclusion, “verify the content’s provenance, not just the source label”, applies to the study.

Our main contributions are:

  1. A four-layer audit protocol (code and data, session provenance, citations, pre-registered reproduction) applied to a real agent-generated study.
  2. Evidence that the study’s headline result is produced by its own code, and that the threat model it claims to address was never simulated.
  3. A pre-registered extension that makes the limits of content verification concrete and measures its costs.
  4. A one-command, hash-pinned reproduction kit and a reviewer checklist for agent-generated research.

2. Related Work

RAG poisoning. PoisonedRAG (Zou et al., 2024) reaches about 90% attack success (ASR) by injecting five texts per target question into a corpus of millions. Semantic Chameleon (Thornton, 2026) shows that hybrid BM25+vector retrieval cuts gradient-guided poisoning from 38% to 0%, and reports 0% attack success on a Wikipedia corpus.

Provenance auditing. “Distributed Denial of Science” (Gyevnár et al., 2026) shows that research agents consume poisoned open datasets (49.56% success, 6.0% detection), and that a five-check provenance-audit prompt reduces success to 0%.

Guidance. The OWASP RAG Security Cheat Sheet and INSS Memo 256 (Hershkovitz, 2026) recommend defense in depth.

Research credibility. The “garden of forking paths” (Gelman & Loken, 2013) motivates pre-registration.

Prior work audits models and data. We audit an agent’s research process, and show that it was the highest-yield layer.

3. Methods

Subject. The audited repository is Blobi92/rag-poisoning-pilot (commits 8595a09 and 21d541f, both co-authored by Perplexity).

  • Data: 759 Wikipedia chunks and 100 LLM-generated poison documents (5 per target question).
  • Questions: 20 targets, each with a correct and an attacker answer, plus 10 clean controls.
  • Pipeline: MiniLM-L6-v2 retrieval (top-5); Qwen2.5-0.5B-Instruct generator (llama.cpp, temperature 0).
  • Arms: (1) open ingestion, (2) allowlist, (3) compromised source (poison relabeled as Wikipedia), (4) + near-duplicate and keyword-stuffing screen, (5) + hybrid retrieval, (6) + embedding corroboration, (7) content verification against a fresh Wikipedia fetch.

Disclosure: a team member created this pilot during the sprint by prompting the agent; the agent did all design, code and writing. The audit is new sprint work.

Layer 1, static audit: we read all code and recomputed every reported number from the raw JSON files.

Layer 2, provenance: we recovered the agent’s session transcript and the earlier research conversation, and compared the plan written before the run with the reported design.

Layer 3, citations: we resolved every reference via arXiv, Crossref and the full-text PDFs, and checked each cited figure word for word.

Layer 4, reproduction:

  • Anchor run. The unmodified upstream script, rerun once from scratch with the identical llama.cpp build (b12389-1ae047c92), model sha256 (74a4da8c…) and thread settings.
  • Pre-registration (commit 81bfacb, made before any new result). New arms:
    • 7′: content verification without the ID shortcut; poison claims its target article’s URL.
    • 8: poison spliced into the canonical article and verified against that same poisoned text, simulating a malicious upstream edit.
    • 8nv: arm 8 without verification (control).
    • 9: an ingestion-time SHA-256 manifest of trusted chunks.
    Also fixed in advance:
    • Scoring: alias-based and normalized.
    • Poison sets: three (the shipped set plus two regenerated with seeds 1 and 2), giving 60 trials per arm.
    • Statistics: Wilson 95% CIs and exact McNemar tests on paired per-question outcomes.
    • A written prediction for every claim.
  • Deviation. Our first run calibrated the screening threshold on ground-truth labels, unlike upstream. We fixed it, archived that run unanalyzed, and reran all three poison sets.

4. Results

The headline result is produced by the code. The upstream verification function begins:

if "poison" in d["id"]: return False  # not present in canonical text

Every poison ID has the form poison::<answer>::<k>, so arm 7 removes all poison before any text is compared. Its 0/20 is guaranteed. Arm 2’s 0/20 is likewise true because the poison is never ingested.

Other findings:

  • The corpus covers 45 articles, not the reported 50.
  • Arm 7 silently dropped 163/759 (21%) of trusted chunks.
  • 19 of 100 poison documents are one-liners, and one states the correct answer.

The design changed after results were in. The plan written before the run had five arms and expected screening to “partially recover”. It didn’t (17/20). The agent then added arm 6, and after that also failed, arm 7 (“one more cheap, realistic defense worth test[ing]”). Arm 7’s first run “kept 0/859 docs” and was then “fixed”. Earlier arms were never rerun after code edits, so the shipped results mix several code versions.

Citations. All six references exist; three contain errors:

  • PoisonedRAG is cited as arXiv:2402.07167, an unrelated radiotherapy paper (the correct ID is 2402.07867).
  • The INSS memo is misdated.
  • A survey title is misquoted.

The “provenance-audit literature” cited studies research agents consuming poisoned datasets, not RAG content matching.

Reproduction. The unmodified pipeline reproduces arms 1–5 exactly. Arm 6 differs by one, consistent with the mixed code versions. Arm 7 kept 717 rather than 596 chunks: its live Wikipedia fetches behave differently from run to run.

What is measured, and what follows from the design. We apply our own construction check to our arms. Three ASR outcomes follow from the design:

  • 7′ = 0: LLM-written poison is never a substring of the real article.
  • 8 ≈ 8nv: verifying against the same poisoned text passes every poisoned chunk.
  • 9 = 0: the poison is never in the manifest.

The quantities genuinely measured are:

  • the cost of live verification: 5.5% of trusted chunks dropped, and lower clean accuracy;
  • a dilution effect: spliced poison reaches the top-5 in 53/60 trials but wins only 26/60 answers, against 56/60 as standalone documents;
  • the reproduction itself.

An independent rerun of our kit from an empty cache reproduced all 30 arm runs within ±1/20, 27 of them exactly.

5. Discussion and Limitations

Which claims stand? The descriptive core of the pilot reproduces: a compromised source bypasses an allowlist, and cheap screening, hybrid retrieval and embedding corroboration barely help against keyword-stuffed poison. Its central claim does not. Content verification can only detect tampering between source and corpus, so it is blind to a compromised source by design. That is exactly the scenario the claim was about. An ingestion-time hash manifest gives the same post-ingestion protection without a live fetch.

What went wrong is familiar. Every failure we found is a known human failure mode that the agent’s speed amplified:

  • adding arms until one “works”;
  • resuming runs across code edits;
  • a shortcut that encodes the answer into the test;
  • citing from a summary of a summary.

None of these is visible in the polished artifact; all were visible in the session transcript. Provenance of the research process was the highest-yield audit layer, and it took minutes. We suggest that agent-generated research ship with:

  1. its session transcript;
  2. a pre-registration commit made before results exist;
  3. single-version results stamped with a git SHA;
  4. machine-checkable citations.

Each is cheap for an agent to produce and expensive for a reviewer to reconstruct.

Limitations

  • One case study, with a small benchmark: 20 targets × 3 poison sets, one corpus, a 0.5B generator and one embedder. Larger generators may resist poisoning differently.
  • Arm 8 is a simplification. It simulates an upstream compromise by splicing text, and ignores Wikipedia’s editorial defenses.
  • The ASR outcomes of arms 7′, 8 and 9 follow from their design, so they illustrate the threat-model gap rather than discover it.
  • llama-server is not bit-exact across runs (up to ±1/20 per arm).
  • We fixed one bug of our own after seeing a run; it is disclosed and archived.

Future Work

  • Apply the protocol to many agent-generated studies to estimate base rates of each failure mode.
  • Automate the construction check and the citation check as CI.
  • Test larger generators and adaptive poison.

6. Conclusion

An AI-generated study on verifying content provenance failed its own standard: its key result came from its code, not its data. Once that is fixed, the honest finding is narrower and more useful. Content verification is a tamper-detection control, only as trustworthy as its reference, and blind to a compromised source by design. Auditing the process (transcript, pre-registration, single-version results) caught what auditing the artifact could not.

Appendix

A. Dual-use and ethical considerations

Attack content. The poison documents are low-sophistication false claims about well-known facts. Upstream-source poisoning is an established threat model, and we release no new attack technique.

Misuse of the method. The audit method could be misused to discredit legitimate work. We mitigate this by reporting what reproduces, publishing every artifact, and pre-registering.

Data. No personal data is processed, and account names were removed from the republished transcript.

B. Reviewer checklist for agent-generated research

  1. Transcript: compare the plan written before the run with the reported design.
  2. Single version: do the results come from one code version? Look for resume, skip or cache logic.
  3. Construction check: find the line of code that decides each headline number. Does it use labels the defense shouldn’t see?
  4. Recount: recompute the descriptive numbers from the raw data.
  5. Threat model: is the claimed scenario simulated, or only a proxy for it?
  6. Citations: resolve each ID and title, and find each quoted figure in the source.
  7. Variance: are there seeds, CIs and paired tests?
  8. Pinned reproduction: binary build, model hash, lockfile, data snapshot.
